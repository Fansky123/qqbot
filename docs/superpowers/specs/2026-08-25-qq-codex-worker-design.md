# QQ Codex 员工设计说明

日期：2026-08-25

## 1. 背景与目标

公司员工需要在离开电脑时，通过指定 QQ 群给 Codex 安排代码任务。系统应接收任务、确认需求、在预配置仓库中执行修改与测试、自动提交并推送任务分支，并由管理员分别批准合并到 RC 分支和部署到 RC 环境。

第一版运行在当前 Linux 电脑上，后续可迁移到公司服务器。系统只接入 RC 环境，不接触生产环境。

成功标准：

- 白名单员工可以在指定 QQ 群创建、确认、补充、查询和取消任务。
- 每个任务在独立 Git 分支和 worktree 中运行，同一项目允许多个任务并行。
- Codex 完成配置的检查后自动提交，调度服务自动推送任务分支。
- 只有管理员能够批准合并和 RC 部署，两个审批相互独立。
- 群消息不能直接成为 Shell 命令、文件路径、Git 引用或部署参数。
- 服务重启、NapCat 断线、Codex 失败、合并冲突和部署失败均有明确且可审计的处理结果。

## 2. 已选择方案

采用以下链路：

```text
公司 QQ 群
    -> 专用普通 QQ 账号
    -> NapCat / OneBot 11
    -> Go 调度服务
    -> Codex CLI + Git worktree
```

选择普通 QQ 与 NapCat 是为了满足普通 QQ 账号作为机器人的需求。该方案属于非官方 QQ 接入，存在风控、掉线和封号风险，因此必须使用专用 QQ 号，不使用员工或管理员的主账号。

没有选择的方案：

- QQ 官方机器人 API：合规性和稳定性更好，但不符合本次普通 QQ 账号接入选择。
- QQ 官方 API + OneBot 12 网关：具备跨平台抽象，但组件更多，且仍不满足普通 QQ 账号接入选择。

NapCat 的主要兼容接口为 OneBot 11，因此本项目按 OneBot 11 开发，不按最初参考的 OneBot 12 开发。

## 3. 系统边界

### 3.1 第一版包含

- NapCat OneBot 11 正向 WebSocket 客户端和自动重连。
- 指定群、员工与管理员白名单。
- 多项目配置和项目简称解析。
- 任务草稿、确认、补充、取消和状态查询。
- SQLite 任务状态、审批记录和审计日志。
- 每任务独立分支和 Git worktree。
- `codex exec` 启动、JSONL 进度解析、超时、取消和会话继续。
- 检查、提交、任务分支推送、管理员批准合并。
- 管理员单独批准 RC 部署。
- 低噪声群通知和本地详细日志。

### 3.2 第一版不包含

- 生产环境或生产凭据。
- Web 管理后台。
- GitHub、GitLab 或 Gitea 的 PR/MR API 集成。
- 定时任务、图片指令或语音指令。
- 多个 QQ 机器人实例。
- 跨机器任务调度和分布式 worker。
- 从 QQ 群执行任意 Shell 命令。
- 自动回滚 RC 环境。

## 4. 组件设计

### 4.1 OneBot 适配器

职责：

- 连接本机 NapCat WebSocket，使用访问令牌鉴权。
- 解析 OneBot 11 群消息事件并发送群消息。
- 只接收配置的群 ID；忽略私聊和其它群的任务指令。
- 将 QQ ID、群 ID 和消息 ID 保持为字符串，避免数值精度问题。
- 对回复内容进行 OneBot/CQ 消息转义，避免用户内容被解释为消息控制码。
- 使用有限退避自动重连；重连不重复消费已经持久化的消息 ID。

NapCat 只监听 `127.0.0.1`，不得将 OneBot 端口直接暴露到局域网或公网。

### 4.2 命令与权限服务

职责：

- 识别明确的 `@Codex [项目简称] 任务描述` 格式。
- 校验群 ID、员工白名单和管理员白名单。
- 把自然语言任务保存为数据，不作为命令、路径或 Git 参数。
- 校验任务所有权：任务发起人和管理员可补充、取消和查询任务。
- 只允许管理员批准合并与部署。

支持的第一版命令：

```text
@Codex [项目简称] <任务描述>
确认 #<任务编号>
补充 #<任务编号> <补充内容>
取消 #<任务编号>
状态 #<任务编号>
日志 #<任务编号>
批准合并 #<任务编号>
批准部署 #<任务编号>
```

所有改变状态的命令都记录 QQ 用户、群、消息 ID 和时间。重复处理同一消息 ID 必须是幂等操作。

### 4.3 项目注册表

项目只能由本地配置预先注册。每个项目必须提供：

- 唯一项目 ID 和一个或多个群内简称。
- 规范化后的仓库绝对路径。
- 允许创建 worktree 的根目录。
- 基准分支、RC 分支和 Git 远端名称。
- 至少一个必须通过的检查命令。
- RC 部署操作 ID。
- 任务并发上限、Codex 超时和日志保留时间。

命令以参数数组配置和执行，不使用可插值的 Shell 字符串。例如检查命令保存为 `['go', 'test', './...']`，而不是 `go test ${USER_INPUT}`。

启动时必须验证：仓库存在、远端存在、分支名合法、路径位于允许根目录内、命令可执行。配置不合法的项目保持禁用状态，不能接收任务。

### 4.4 任务调度器

职责：

- 为任务生成不可复用的任务编号。
- 持久化状态后再发送确认消息。
- 按项目并发上限调度；每个任务使用独立 worktree。
- 每个项目设置独立的合并锁和部署锁。
- 服务重启时恢复排队任务，将中断的执行任务标记为需要人工恢复。

同一项目的 Codex 任务可以并行，但该项目同时只能执行一次合并或一次部署。

### 4.5 Codex runner

runner 在任务 worktree 中使用非交互模式运行 Codex：

```text
codex exec --sandbox workspace-write --add-dir <git-common-dir> --json <受控任务提示>
```

实现要求：

- 使用参数数组启动子进程，不经过 Shell。
- 只向子进程传递允许的环境变量和公司 Codex 凭据。
- 不向 Codex 进程传递 NapCat、Git 推送或 RC 部署凭据。
- 只把当前仓库解析后的 Git common dir 作为额外可写目录，使 worktree 中的 `git commit` 可以更新共享 Git 元数据；任务结束后校验分支和提交引用未越界。
- 解析 JSONL 事件，保存完整日志，只从受支持事件生成状态摘要。
- 保存 Codex 会话 ID；`补充` 使用指定会话继续，不使用全局 `--last`。
- 支持上下文超时和管理员/发起人取消；取消后终止完整进程组。
- 任务提示明确限制项目、目标、检查命令和交付要求，并指示 Codex 在检查通过后提交变更。

Codex 官方文档确认 `codex exec` 适用于脚本与 CI，支持 JSONL 输出、显式沙箱和会话继续：<https://learn.chatgpt.com/docs/non-interactive-mode>。

### 4.6 Git 与 RC 操作器

Codex 负责在任务 worktree 中修改、检查和创建提交。Go 服务负责验证和执行有凭据的 Git/RC 操作。

任务开始：

1. 获取远端最新状态。
2. 从配置的 `origin/<base_branch>` 创建 `codex/<task-id>` 分支。
3. 在受控 worktree 根目录创建任务 worktree。
4. 记录基准提交哈希。

任务完成：

1. 依次运行项目注册表中的检查命令。
2. 验证工作区干净，任务分支相对基准提交至少新增一个提交。
3. 验证提交只修改仓库内文件，且当前分支名称与任务一致。
4. 以普通推送将任务提交写入固定的远端任务分支；禁止 force push。
5. 保存并上报不可变的任务提交哈希，进入等待合并状态。

批准合并：

1. 校验审批人是管理员。
2. 校验远端任务分支仍指向上报的任务提交哈希。
3. 获取最新 RC 分支，在临时合并 worktree 中执行非快进合并。
4. 重新运行配置的检查命令。
5. 无冲突且检查通过后普通推送到 RC 分支；远端已变化时推送失败并停止。
6. 保存新的 RC 提交哈希，进入等待部署状态。

批准部署：

1. 校验审批人是管理员。
2. 校验 RC 远端仍包含并指向已批准的 RC 提交状态。
3. 运行项目注册的固定 RC 部署操作。
4. 保存部署目标、RC 提交哈希、审批人和结果。

Git 推送、合并与部署所需凭据不得保存在 Codex 可读的项目目录中。接入真实 RC 前，凭据操作应由独立 OS 身份或受限操作辅助程序执行；辅助程序根据项目 ID 和任务 ID 解析固定路径、远端和部署操作，不接受群消息提供的命令或路径。初期本地端到端测试使用无真实凭据的本地裸仓库和假部署程序。

### 4.7 持久化与日志

SQLite 使用 WAL 模式。最少包含以下逻辑实体：

- `tasks`：任务编号、项目、发起人、需求、状态、分支、worktree、Codex 会话、基准/任务/RC 提交哈希和时间。
- `task_inputs`：创建、确认和补充的原始消息及发送人。
- `approvals`：合并或部署、审批人、绑定提交哈希、消息 ID、结果和时间。
- `processed_messages`：用于 OneBot 消息幂等处理。
- `audit_events`：只追加的状态变化和外部操作记录。

详细 Codex、检查、Git 和部署日志按任务保存到受控日志目录。群内 `日志` 命令只返回经过长度限制和敏感信息过滤的摘要，不回传原始环境变量、凭据或超长命令输出。

## 5. 任务状态机

主状态：

```text
draft
  -> awaiting_confirmation
  -> queued
  -> running
  -> checking
  -> pushed
  -> awaiting_merge_approval
  -> merging
  -> merged
  -> awaiting_deploy_approval
  -> deploying
  -> deployed
```

终止或暂停状态：

- `blocked`：需要任务发起人补充信息；补充后恢复同一 Codex 会话。
- `failed`：Codex、检查、Git 或持久化操作失败。
- `cancelled`：发起人或管理员取消。
- `merge_conflict`：合并冲突或合并后检查失败，需要人工处理。
- `deploy_failed`：RC 部署失败；只有管理员可以重新批准重试。

状态转换必须由服务端规则驱动，不能由 Codex 输出或群消息自由指定。

任务已经推送后收到补充要求时，原合并审批立即失效。系统恢复 Codex 会话、产生新提交并更新远端任务分支；新的提交哈希必须重新获得合并审批。RC 合并完成后不再接受任务补充，后续改动必须创建新任务。

## 6. 群内交互

### 6.1 创建与确认

员工发送任务后，机器人创建草稿并回复：

- 任务编号和项目。
- 对目标的理解。
- 预计修改范围。
- 将执行的检查。
- 已识别风险或需要澄清的问题。

只有任务发起人回复 `确认 #<任务编号>` 后，任务才进入队列。存在歧义时保持待确认状态，不创建分支或 worktree。

### 6.2 低噪声通知

机器人只主动通知：

- 任务开始。
- 任务被阻塞并需要输入。
- 任务失败。
- 任务完成并已推送。
- 合并或部署结果。

常规 Codex 思考、命令和阶段进度只写本地日志，员工通过 `状态` 或 `日志` 主动查询。

### 6.3 完成摘要

完成消息包含：

- 任务分支和任务提交哈希。
- 变更摘要。
- 每个检查命令的通过/失败结果。
- 已知限制和后续建议。
- 下一条允许的管理员命令。

QQ 单条消息超长时分段发送，并限制总段数；完整内容保存在任务日志中。

## 7. 安全模型

- 专用 QQ 账号只加入指定公司群。
- NapCat 使用令牌并仅监听本机回环地址。
- 员工白名单可创建、确认、补充、查询和取消自己的任务。
- 管理员白名单可操作所有任务，并独占合并与部署审批。
- QQ 消息只作为任务文本或严格语法中的任务编号处理。
- 项目、路径、分支、检查和部署操作全部从本地注册表解析。
- Codex 使用最小写权限沙箱和环境变量允许列表。
- Codex 不接收 Git 推送与 RC 部署凭据。
- 任务推送、合并和部署均绑定精确提交哈希。
- 不允许 force push，不允许从 QQ 请求覆盖分支或修改项目配置。
- 不配置生产仓库、生产分支、生产主机或生产密钥。
- 日志输出在保存和回群前进行敏感信息过滤。

普通 QQ + NapCat 的封号风险无法由应用层消除。账号异常时系统停止接收新任务，已有本地任务和 Git 分支仍可审计和恢复。

## 8. 故障处理

- NapCat 断线：有限退避重连；依赖消息 ID 和 SQLite 去重。
- SQLite 写入失败：不执行对应外部副作用，任务进入失败状态。
- Codex 超时：终止进程组，保留 worktree 和日志，标记失败。
- Codex 需要信息：标记阻塞并通知发起人；补充后恢复指定会话。
- 检查失败：允许 Codex 在单次任务预算内修复；最终仍失败则不推送，保留本地分支。
- 推送失败：不强推；刷新远端状态并报告失败。
- 合并冲突：不修改远端 RC，标记 `merge_conflict`。
- RC 分支在审批后变化：使当前部署审批无效，要求管理员基于新的 RC 哈希重新批准。
- 部署失败：标记 `deploy_failed`，不自动回滚、不无限重试。
- 服务重启：恢复草稿和排队任务；运行中、合并中和部署中的任务转为需要人工检查，禁止自动重放外部操作。

取消和失败任务的 worktree、分支与日志默认保留七天，再由维护命令清理。远端任务分支不自动删除。

## 9. 测试策略

### 9.1 单元测试

- OneBot 事件解析、CQ 转义和消息分段。
- 命令解析、任务编号校验和消息幂等。
- 员工/管理员权限矩阵。
- 状态机所有允许和拒绝的转换。
- 项目别名、路径和 Git 引用校验。
- 环境变量过滤和日志脱敏。
- 审批与提交哈希绑定。

### 9.2 集成测试

- 模拟 OneBot WebSocket 的连接、断线、重连和重复消息。
- 使用临时工作仓库与本地裸远端验证 worktree、并发任务、普通推送和远端变化。
- 使用存在冲突的临时分支验证 RC 合并停止。
- 使用假 `codex` 程序产生 JSONL、阻塞、超时、失败和会话继续事件。
- 使用假部署操作验证审批、串行化、失败和重试。
- 进程重启后验证任务恢复且外部操作不被重复执行。

### 9.3 端到端验收

先使用专用 QQ、测试群、本地测试仓库和假 RC 部署操作完成完整流程。随后选择一个非关键 RC 仓库，配置真实检查、任务分支推送和受限 RC 部署操作。验收覆盖：

- 两名员工在同一项目并行执行两个无冲突任务。
- 非白名单成员和非指定群无法创建任务。
- 发起人确认、补充和取消权限正确。
- 管理员之外无法合并或部署。
- 已批准提交变化后审批失效。
- 合并冲突和部署失败不会改变预期之外的远端或环境状态。

## 10. 配置与迁移原则

第一版采用单进程 Go 服务、SQLite 和本地文件日志。所有可迁移路径通过配置指定，不把当前用户名或绝对部署目录写死在代码中。

迁移到服务器时需要搬迁：

- 项目注册表和白名单配置。
- SQLite 数据库和任务日志。
- 仓库镜像或重新克隆的仓库。
- 公司 Codex 凭据。
- NapCat 配置与专用 QQ 登录状态。
- 受限 Git/RC 操作辅助程序及其独立凭据。

迁移不会改变 OneBot、任务状态机或群内命令协议。服务器化、进程守护、备份和监控在迁移实施计划中单独设计，不进入第一版本地实现范围。

## 11. 实施约束

- 使用 Go 标准库和项目已有依赖优先；仅为 WebSocket、SQLite 等明确需求引入成熟依赖。
- 所有外部副作用前先持久化意图，操作后持久化结果。
- 一个模块只负责一个边界：OneBot、命令/权限、调度、Codex、Git/RC、存储、通知相互分离。
- 不实现未列入第一版范围的管理界面、插件系统或通用工作流引擎。
