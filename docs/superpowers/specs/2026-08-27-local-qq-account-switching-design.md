# 本机 QQ 机器人账号自动切换设计

日期：2026-08-27

## 目标

让本机 QQ Codex Worker 不再绑定专用 QQ 号。用户可以在 NapCat 登录窗口扫码选择任意已加入指定群的 QQ，系统自动识别当前账号、校验群成员关系、启动 Worker，并将成功账号记为下次默认账号。

指定群、员工和管理员仍分别由 `allowed_group_ids`、`employee_ids` 和 `admin_ids` 配置。三者均支持多个 ID，换机器人账号时不得改写。

本阶段只处理本机运行，不引入服务器部署或系统级守护服务。

## 选定方案

采用“Worker 自动识别 + 本机统一启动器”：

- Worker 在每次建立 OneBot WebSocket 会话时调用 `get_login_info`，以返回的 `user_id` 作为本次会话的机器人账号。
- Worker 使用该账号校验事件的 `self_id`，并判断消息中的 `at` 是否真正指向当前机器人。
- 启动器在启动 Worker 前调用只读探测模式，获取当前账号和群列表，并确认所有 `allowed_group_ids` 都已加入。
- 只有显式执行换号命令且校验成功后，启动器才保存新的默认账号。
- NapCat 已有的通用 `onebot11.json` 继续作为新账号的默认 OneBot 配置；无需为每个 QQ 手工创建配置。

固定 `self_id` 仍保持向后兼容。本机配置使用自动模式，其他部署若继续配置固定 ID，其行为不变。

不采用“扫码后直接改写整个 Worker JSON”的方案，因为它会把账号发现与用户维护的群、员工及项目配置混在一起，并产生配置与实际连接短暂不同步的窗口。

## 配置边界

本机配置示例：

```json
{
  "onebot": {
    "url": "ws://127.0.0.1:3001",
    "access_token_env": "NAPCAT_ACCESS_TOKEN",
    "self_id": "auto"
  },
  "allowed_group_ids": [
    "2163011680",
    "另一个群号"
  ],
  "employee_ids": [
    "员工QQ号"
  ],
  "admin_ids": [
    "管理员QQ号"
  ]
}
```

`self_id: "auto"` 只改变机器人账号的来源。它不扩大消息授权范围：

- 私聊不进入现有应用处理流程。
- 不在 `allowed_group_ids` 中的群消息被忽略。
- 不在 `employee_ids` 中的用户不能咨询或创建任务。
- 管理操作仍要求 `admin_ids`，且管理员必须同时是员工。
- 现有的“必须真正 @当前机器人”规则保持不变。

使用个人 QQ 作为机器人账号时，NapCat 本身仍登录该 QQ，但 Worker 只处理上述授权边界内的群消息。

## OneBot 会话识别

每次 WebSocket 连接成功后，客户端先发送 `get_login_info`，并严格校验成功响应中的数字 `user_id`。识别完成前不向应用层投递群消息。

本次连接后续只接受 `event.self_id` 与已识别账号一致的事件；不一致的事件被忽略。消息中的 `at` 段也与已识别账号比较，防止把 `@其他成员` 或 `@全体成员` 当作触发机器人。

断线重连后重新执行账号识别。因此 NapCat 登录态变化不会沿用旧会话的账号。固定 `self_id` 模式除自动探测外仍执行原有固定 ID 校验。

探测模式复用同一套 OneBot 鉴权和响应解析，但只执行：

- `get_login_info`：返回当前 QQ 号和昵称；
- `get_group_list`：返回当前账号已加入的群 ID。

探测结果以有界 JSON 输出给本机启动器，不输出 OneBot 令牌或 Codex 凭据。探测模式不加载数据库、项目仓库、Codex、Git 或部署能力。

## 本机命令

安装后提供统一命令：

```bash
qqcodex-local start
qqcodex-local switch-account
qqcodex-local status
qqcodex-local stop
```

### 正常启动

`qqcodex-local start` 执行以下流程：

1. 检查 NapCat、Worker、端口和受管 PID 状态，不接管或终止普通 QQ 进程。
2. 使用上次成功保存的账号启动 NapCat；快速登录失效时保留二维码登录兜底。
3. 等待 OneBot 端点可用，并在限定时间内探测当前账号与群列表。
4. 当前账号必须与已保存账号一致；首次运行没有保存账号时允许采用当前扫码账号。
5. 校验所有 `allowed_group_ids` 均在当前账号群列表中。
6. 校验通过后启动 Worker，并在前台显示运行日志。

普通 QQ 客户端已运行、端口被无关进程占用或已存在非受管 Worker 时，命令直接失败并说明原因，不自动杀进程。

### 扫码换号

`qqcodex-local switch-account` 执行以下事务：

1. 保存旧的默认账号状态并停止由启动器管理的 Worker 和 NapCat。
2. 临时禁用旧账号快速登录，启动 NapCat 二维码登录界面。
3. 等待扫码，探测新账号及其群列表。
4. 校验所有指定群；缺少任意群时列出群号并拒绝启动 Worker。
5. 校验成功后，原子写入本地账号缓存和 NapCat 自动登录账号，再启动 Worker。
6. 扫码取消、超时、探测失败或群校验失败时停止本次 NapCat，并恢复旧账号状态。

只有 `switch-account` 可以用不同账号覆盖已有默认账号，避免普通 `start` 静默采用错误的个人 QQ。

### 状态与停止

`status` 分别显示 NapCat、OneBot 登录账号和 Worker 是否在线，不显示令牌。`stop` 只向启动器记录的受管 PID 发送正常终止信号，不使用按进程名批量终止，也不关闭普通 QQ。

## 本地状态与权限

机器相关脚本和状态保留在现有本地目录：

```text
/home/fanfan007/.local/share/napcat/
/home/fanfan007/.local/share/qqcodex-worker/
/home/fanfan007/.local/bin/qqcodex-local
```

账号缓存、PID 文件、NapCat WebUI 配置和 OneBot 配置使用仅当前用户可读写的权限。更新 JSON 或账号缓存时先写同目录临时文件，再原子替换，避免中断留下半份配置。

OneBot WebSocket 与 NapCat WebUI 继续只监听 `127.0.0.1`。访问令牌从现有受限文件载入，不写入命令参数、探测输出或日志。Codex Key 的隔离与继承规则不变。

## 失败行为

- 快速登录失效：NapCat 显示二维码；超时后退出且不覆盖账号缓存。
- 扫码账号不同：普通 `start` 拒绝采用，提示使用 `switch-account`。
- 未加入指定群：列出缺失群号，不启动 Worker。
- OneBot 无法连接或返回无效账号：重试至超时，不猜测配置文件名或历史账号。
- Worker 运行期间 OneBot 掉线：沿用现有重连；重连成功后重新识别账号。
- 受管状态陈旧：只有 PID 与预期进程身份匹配时才允许清理或终止。
- 换号事务失败：恢复旧账号缓存和 NapCat 自动登录设置；不修改群、员工、管理员或项目配置。

## 测试与验收

实现按测试驱动完成：

- OneBot 单元测试覆盖自动账号识别、固定 ID 兼容、无效 `get_login_info` 响应、事件账号不匹配及 `@当前机器人` 判断。
- 配置测试覆盖 `self_id: "auto"`、固定数字 ID 和非法值。
- 探测测试覆盖登录信息、多个群、缺失群、动作失败、断线和超时，且输出中不含令牌。
- 启动器测试使用临时目录和假进程覆盖正常启动、首次扫码、显式换号、事务回滚、普通 QQ 冲突、陈旧 PID 以及多群校验。
- 全量运行 `go test ./...`，并执行 shell 静态语法检查。
- 本机验收使用两个可登录 QQ：换号扫码后在每个配置群中 `@新机器人` 完成一次咨询；再创建一条测试任务并停在需要确认的安全阶段。
- 重启后确认自动登录上次账号，旧账号不再响应，未配置群和未授权用户仍被忽略。

真实账号无法自动化扫码，因此最终本机验收需要用户完成二维码确认；其余步骤由启动器自动执行。

## 非目标

- 自动申请加入 QQ 群或自动邀请机器人。
- 修改 `allowed_group_ids`、`employee_ids`、`admin_ids` 或项目配置。
- 同时运行多个机器人 QQ。
- 处理私聊或未 @机器人的普通群消息。
- 服务器部署、开机自启、无人值守账号恢复或生产环境凭据管理。
